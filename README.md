# CQA — контроль качества диалогов поддержки

Команда **Bratva Aitu** · Data Challenge'26 · кейс Freedom Broker «Conversation Quality Analytics».

Система оценивает диалоги операторов поддержки по настраиваемому чек-листу из 8 критериев. По каждому критерию LLM возвращает значение, обоснование и номера реплик-доказательств. Итоговый балл считает код, а не модель. Есть апелляции, версии чек-листа, журнал всех вызовов модели и выгрузка `results.json` по контракту организаторов.

## Результаты

| Набор | Файл | Диалогов | Статус ok | Модель | Стоимость |
|---|---|---|---|---|---|
| Контрольный (`group_id=FBroker`) | [results/prod/results.json](results/prod/results.json) | 10 | 10 | openai/gpt-5.5 | $0,99 |
| DEV | [results/dev/results.json](results/dev/results.json) | 65 | 65 | openai/gpt-5.5 | $6,95 |

**Стоимость одной оценки диалога** около **$0,10** на gpt-5.5 по прайсу $5 / $30 за 1M токенов: 8 вызовов модели, по одному на критерий, около 10 секунд на диалог. Это верхняя граница: общий префикс промптов частично кешируется и стоит дешевле. Для массовой проверки модель меняется одной переменной `CQA_OPENAI_MODEL`, например на gpt-5.5-mini, она примерно в 20 раз дешевле. Оба файла проходят встроенный валидатор: JSON Schema плюс семантические проверки.

Файлы `results*.json` сформированы кодом командой `make prod GROUP=FBroker` и вручную не редактировались. В них только значения модели. Решения по апелляциям хранятся отдельно и на файл не влияют.

## Как это работает

```
API организаторов ─► ingest ─► нормализация ─► факты из кода ─► 8 вызовов LLM ─► валидация ─► расчёт балла ─► БД ─► results.json
  (group_id)                    реплики с 1      приветствие,      по одному на       домен,         Σ баллов /
                                системные        имя, прощание,    критерий,          реплики,       Σ весов × 100,
                                события          события чата      JSON Schema        повтор при     half-up
                                                                                      ошибке
```

1. **Загрузка.** Диалоги берутся из Power Automate API организаторов по `group_id`, ответ сохраняется снапшотом. Есть повторы при таймаутах.
2. **Подготовка.** Реплики нумеруются с 1 по всему транскрипту, как в контракте. Системные события RU/KZ/EN распознаются словарём. Код заранее вычисляет факты: есть ли приветствие и имя в первой реплике оператора, есть ли прощание, подтверждалась ли личность, чем закончился чат. Факты передаются модели как подсказка. Персональные данные маскируются до отправки.
3. **Оценка.** Каждый критерий оценивается отдельным вызовом. Так одна ошибка оператора не перетекает во все критерии сразу. Ответ модели строго ограничен JSON Schema: значение из домена критерия, обоснование, реплики-доказательства, причина N/A. Код проверяет ответ: значение допустимо, реплики существуют и принадлежат оператору. При ошибке делается один повторный запрос.
4. **Балл.** `итог = Σ баллов / Σ весов применимых критериев × 100`, округление до 2 знаков half-up через `Decimal`. N/A исключается из числителя и знаменателя. Грубые нарушения идут отдельным флагом `critical_flag`. Пример из приложения к гайду, 85,38, покрыт тестом.
5. **Выгрузка.** `results.json` версии 1.0, в порядке диалогов из API, с валидацией перед записью.

## Модели

Основная модель — OpenAI gpt-5.5 через Structured Outputs. Провайдеры подключаемые, порядок задаётся в `CQA_PROVIDER_CHAIN`:

| Провайдер | Как подключён |
|---|---|
| OpenAI | JSON Schema strict |
| Anthropic Claude | tool use с вынужденным вызовом |
| Gemini, DeepSeek | OpenAI-совместимый endpoint |
| Ollama, LM Studio | локально, OpenAI-совместимый endpoint |
| rules | офлайн-правила на фактах из кода, последний резерв |

Если основной провайдер недоступен, запрос уходит следующему по цепочке. В `results.json` поле `model` показывает модели, которые реально выдали оценки, а режим становится `hybrid`, если смешались облачная и локальная модели. Можно включить второе мнение от локальной модели: расхождения видны в карточке диалога.

## Интерфейс

Статический HTML/CSS/JS без сборки в стиле Dynamics 365 Customer Service с акцентом Freedom. Его отдаёт тот же API на `http://127.0.0.1:8000`.

- **Диалоги.** Список с итогами, грубыми ошибками и апелляциями, запуск оценки выбранных или всех.
- **Карточка диалога.** Транскрипт с подсветкой реплик-доказательств, критерии с обоснованием, формула балла, факты из кода, вызовы модели, история оценок, аудиоплеер для звонков.
- **Апелляции.** Оператор оспаривает критерий, проверяющий подтверждает или меняет значение с причиной, итог пересчитывается.
- **Чек-листы.** Редактирование критериев, весов, шкал и правил N/A. Каждое сохранение — новая версия. Есть активация версии, сравнение версий на наборе и переоценка.
- **Запуски и журнал.** Прогресс, стоимость, каждый вызов модели с ответом и хешем промпта.
- **Нарушения, аналитика, модели, сдача результатов.** Последний экран — предпросмотр `results.json` и проверки перед push.

REST API документирован на `/api/docs`, метрики Prometheus отдаются на `/metrics`.

## Запуск

```bash
cp .env.example .env          # вписать CQA_ORG_API_URL и ключ провайдера
make setup                    # venv + зависимости (нужен uv)
make test                     # тесты движка расчёта
make dev                      # API + интерфейс на http://127.0.0.1:8000
```

Контрольный час одной командой:

```bash
make prod GROUP=<group_id>    # загрузка → оценка → results/prod/results.json → валидация
```

Отдельные шаги: `make fetch GROUP=DEV`, `make eval GROUP=DEV`, `make export GROUP=DEV TARGET=dev`, `make validate FILE=results/prod/results.json EXPECT=10`.

## Архитектура и развёртывание

Один Docker-образ для всех ролей (`CQA_SERVICE=api|worker`):

- **api** — FastAPI, REST и статика интерфейса, без состояния, масштабируется горизонтально за балансировщиком;
- **worker** — забирает задания оценки из Redis Streams и масштабируется по длине очереди;
- **PostgreSQL** — диалоги, версии чек-листа, оценки с историей, вызовы модели, апелляции, выгрузки;
- **Redis** — очередь заданий;
- **Prometheus и Grafana** — метрики вызовов, задержек, стоимости и ошибок.

```bash
make up      # postgres + redis + api + 2 workers
make obs     # + Prometheus :9090 и Grafana :3000
```

В Kubernetes (DigitalOcean DOKS) то же разворачивается манифестами из `deploy/k8s`: API с HPA за ingress-nginx и балансировщиком DigitalOcean, воркеры с HPA или KEDA по длине очереди Redis, PostgreSQL и Redis.

```bash
cp deploy/k8s/secret.example.yaml deploy/k8s/secret.yaml   # вписать ключи, файл в .gitignore
kubectl apply -f deploy/k8s/secret.yaml && kubectl apply -k deploy/k8s
```

Без Redis и PostgreSQL система работает на SQLite с фоновыми заданиями внутри процесса API. Так она запускается на ноутбуке во время контрольного часа.

## Структура

```
backend/cqa/
  scoring.py            расчёт балла (Fraction → Decimal, half-up), N/A, критический флаг
  checklist_default.py  чек-лист заказчика как данные + уточнения из чата хакатона
  preprocess.py         нормализация, системные события, факты, маскирование ПДн
  evaluator.py          промпты, схема ответа, валидация, оценка диалога
  llm/router.py         провайдеры, цепочка резервов, кеш, бюджет, учёт стоимости
  export.py             контракт results.json 1.0 и валидатор
  pipeline.py           ingest → evaluate → export
  db.py, api/app.py, worker.py
frontend/               интерфейс
results/                dev и prod
```
